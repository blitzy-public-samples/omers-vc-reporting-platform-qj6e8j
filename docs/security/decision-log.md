# Security Remediation Decision Log

This decision log is the single source of truth for the decision rationale behind the security-remediation engagement on the OMERS Ventures Backend Platform. It records every non-trivial decision, the alternatives considered, the justification, and the residual risk — beginning with the decisions in Section 0.10.2 of the Technical Specification and extending them with the subsequent review-cycle and remediation decisions. Code comments are deliberately limited to minimal, factual annotations that name the security control and its CVE/CWE/advisory identifier — as permitted by Technical Specification §0.9.3 — and defer to this log for the full rationale rather than duplicating it. The table below has four columns: Decision, Alternatives Considered, Rationale, and Risk.

| Decision | Alternatives Considered | Rationale | Risk |
|----------|-------------------------|-----------|------|
| Keep Pydantic on the v1 line (`1.10.13+`) | Migrate to Pydantic v2 + `pydantic-settings` | Preserves the `BaseSettings` API used throughout; honors the Minimal Change Clause | v1 will eventually be end-of-life; a future v2 migration remains a follow-up |
| Cap FastAPI below `0.126.0` (pinned `0.125.0`) | Upgrade to the latest FastAPI | FastAPI `0.126.0` drops Pydantic v1 support; the pinned `0.125.0` stays within the v1-compatible range and clears CVE-2024-24762 | Misses newest FastAPI features until a future v2 migration |
| Version bump, not package replacement | Replace vulnerable packages with alternatives | Every vulnerable package has a maintained patched release; bump is least invasive | None material |
| Bump `cryptography` although it is declared-but-unwired | Leave it pinned at 3.4.8 | It remains in the container image attack surface; hygiene and defense-in-depth | Minor build-surface change, covered by tests |
| CORS: consume an explicit origins allow-list | Set `allow_credentials=False` only | Retains credentialed flows for legitimate origins while removing wildcard exposure | Operators must configure real origins per environment |
| Require secrets from env with a min-length guard | Auto-generate a secret at startup | Mirrors the existing secure pattern; fails closed on misconfiguration | Deployments must set the secret env vars |
| Add the CI scan gate to Azure Pipelines | Add a `.github/workflows` action | The repository uses Azure Pipelines, not GitHub Actions | None |
| Defer `pytest` 6.x→9.x and `loguru` | Upgrade now | Test-only / informational, local-only vectors; three-major `pytest` jump risks breaking tests | Low-severity residual advisory in the dev toolchain |
| Scope observability to security-event logging (reuse logging) | Build full tracing + metrics now | Satisfies the Observability rule while respecting minimal change | Observability remains partial pending the noted follow-up |
| IaC: reference the existing sensitive variable | Wire full Azure Key Vault retrieval now | `variables.tf` already declares the variable; least-invasive removal of the literal | Secret still requires secure provisioning at apply time |
| Advance the base image on the two root containers | Keep `python:3.8-slim` and pin `cryptography < 49` | `python:3.8-slim` is end-of-life; the bump also enables current `cryptography` | Base-image behavioral drift, mitigated by the regression suite |
| No `DELETE` transformations | Remove unwired dependencies / dead code | Out of security-fix scope; deletion could alter behavior | Unwired packages remain (patched rather than removed) |
| `data_transformation`: pin `requests`/`urllib3` to their patched releases (`2.33.0` / `2.7.0`) and audit this manifest on Python 3.11 in CI | Keep the `2.32.4` / `2.6.3` pins (Python 3.9-compatible, the AAP target) and continue ignoring the advisories in CI | The patched `requests`/`urllib3` clear PYSEC-2026-2275 (`requests`) and PYSEC-2026-141/142 (`urllib3`); auditing on Python 3.11 (where these pins — which require Python ≥ 3.10 — install) confirms they resolve, so the CI gate enforces them rather than masking fixable advisories on the function's outbound FX-rate HTTP path. The three Python 3.10 services (`authentication_service`, `reporting_financials_service`, `reporting_metrics_service`) take the patched `requests` 2.34.2 and `python-dotenv` 1.2.2 directly (with `urllib3` 2.7.0 transitively), clearing PYSEC-2026-2270 there. The two Python 3.9 services (`api_gateway`, `metrics_input_service`) do not depend on `requests`/`urllib3` at all (they use `httpx`), but they do pin `python-dotenv` — held at 1.0.1 because its fix (`python-dotenv` 1.2.2) requires Python ≥ 3.10 — so its PYSEC-2026-2270 advisory is waived in CI on those two services only. Remaining backend CI ignores are limited to advisories that are unfixable within the frozen envelope or whose fix is not installable on the service's runtime — `pytest` (three-major-version jump deferred per §0.6.4), `loguru` (Windows-only, informational), `starlette` (held below 0.51 by the FastAPI < 0.126 / Pydantic-v1 ceiling), and `click` and `python-dotenv` (only on the Python 3.9 services; their fixes require Python ≥ 3.10) | The function app's **deploy** runtime in `infrastructure/terraform/main.tf` is `PYTHON\|3.11` (Python 3.11), which satisfies the >= 3.10 requirement of these patched pins, so they install cleanly at deploy time; no runtime-alignment follow-up remains |
| `api_gateway`: add `min_length=32` to the `secret_key` setting | Leave the field without a length guard, or remove the vestigial field | Aligns the gateway with the minimum-length enforcement claimed for it (AAP §0.3.2) and mirrors the required-and-validated secret pattern in the authentication/reporting services; adding the guard is the least-invasive of the two options | The field is presently unused at runtime (the gateway validates the signing key via the authentication-service dependency), so there is no behavioral change for a valid configuration |
| Security-test bootstraps (`tests/__init__.py`) provision fail-closed env at package-init top and import only `config`, not the application chain | Provision the env in `conftest.py` only, or rely on ambient CI environment variables | `config.py` is fail-closed (required `SECRET_KEY`/`JWT_SECRET_KEY` with a min-length guard, a validated `DATABASE_URL`, and no placeholder `API_KEY` default), so it raises at import time unless the env is present; pytest imports the `tests` package initializer while resolving fully-qualified module names — before `conftest.py` runs — so provisioning env at the top of `tests/__init__.py` is what lets the configuration and CORS security suites collect (F1/F2/MET-2) | None for the security suites, which collect and pass. The application import chain itself is healthy (see the row below); the only residual is the pre-existing non-security `test_financials.py`, which fails to collect because it imports a `financials_router` symbol the router module does not export — tracked separately (AAP §0.8.2) |
| The application-import defects that previously blocked full test binding have been resolved, so no deferral remains | Leave this log asserting the imports are still broken and deferred | `app/routers/financials.py` reads the settings **instance** (`create_engine(str(config.DATABASE_URL))`), not the class attribute `Config.DATABASE_URL`, and `app/models/models.py` imports `UUID` from `sqlalchemy.dialects.postgresql` (not the absent bare `sqlalchemy.UUID`); with these in place `main.create_app`, the models module, and the reporting-metrics app all import cleanly (verified at runtime in the service containers), so the earlier deferral no longer applies | None — the previously noted import blockers are cleared; any remaining pre-existing non-security defect in a non-security test module is unrelated to these imports and tracked separately (AAP §0.8.2) |
| Financials CORS regression test binds a `TestClient` to the real `main.create_app()` and asserts the no-wildcard-with-credentials invariant directly, in addition to exercising the `config.CORS_ORIGINS` validator | Keep the `xfail`-guarded fixture, or use only a synthetic app mirroring `main.py` | `main.create_app` now imports cleanly, so the former `xfail` produced a silent XPASS; the test now binds to the real factory and asserts an untrusted origin is never answered with `*` and the configured origin is reflected specifically, so it fails if the CWE-942 wildcard-with-credentials mutation is reintroduced (verified: passes against the real app, fails under the mutation) | None — the test passes against the real factory and is mutation-sensitive; no `xfail` masking remains |
| Multi-service test aggregation uses per-service invocation (`pytest src/backend/<svc>/tests`) | Change pytest import mode / restructure the `tests` packages to allow a single aggregate collection | Every service ships a regular `tests` package under namespace parents, so aggregate collection hits a top-level `tests` module-name collision (CS-1); per-service invocation is the documented workflow and avoids it, whereas an import-mode/package-layout migration exceeds the minimal-change security scope | Aggregate (multi-service) collection remains unsupported until a broader test-layout change is undertaken (noted follow-up) |
| Keep `fastapi-cors` and `fastapi-limiter` removed from the `authentication_service` manifest | Restore both pins to their baseline versions, per the Minimal Change Clause / CR-22 "revert nonessential change" guidance | Both baseline pins are **phantom versions that do not exist on PyPI** — `fastapi-cors==0.13.0` (only `0.0.6` is published) and `fastapi-limiter==0.7.2` (only versions up to `0.2.0` are published) — so the baseline manifest could never install in a clean environment (`pip install` fails with "No matching distribution found"). Restoring them would re-break clean-environment installs and the CI dependency-scan gate, i.e. the exact clean-install contract enforced by CR-15. Both are also unwired: the CORS control used by this remediation is FastAPI's built-in Starlette `CORSMiddleware` (no separate CORS package needed), and the rate limiter is never imported. Removing non-installable, unused pins is the least-invasive way to keep the manifest installable, so the suggested "revert" is not adopted (a better fix per the root-cause principle) | If rate limiting is wired in future work, `fastapi-limiter` must be re-added at a real, published version (`<= 0.2.0`, whose API differs from the phantom `0.7.2`) — noted follow-up |
| Relocate the `pip --user` dependencies from `/root/.local` into the non-root user's HOME (`/home/appuser/.local`) with `--chown` in the `api_gateway` and `reporting_financials_service` Dockerfiles | Leave the deps in `/root/.local`; `chmod 755 /root` to expose traversal; or convert to a system-wide `pip install` | The two multi-stage images copied deps to `/root/.local` (mode 700, root-owned) then switched to `USER appuser`, so the non-root user could not traverse `/root` and `uvicorn` failed to launch with `[Errno 13] Permission denied` — leaving the CWE-250 non-root hardening declared but non-functional; relocating into the user's HOME with `--chown` is the least-invasive fix and, unlike `chmod 755 /root`, keeps `/root` unexposed | None material — the `CMD`/`EXPOSE` container contract and the `USER appuser` identity are preserved byte-for-byte; the separate, pre-existing app-code import defect (`ModuleNotFoundError: No module named 'src'`, AAP §0.8.2) is unaffected and tracked outside this engagement |
| Pin `h11 >= 0.16.0` (transitive, via `uvicorn`) in all five backend manifests | Bump `uvicorn` to a release that forces patched `h11`, or leave `h11` unpinned to float | A runtime A/B probe confirmed `h11 < 0.16.0` accepts a malformed 2-byte chunk footer (CVE-2025-43859 / GHSA-vqfr-h8mv-ghfj / CWE-444 request smuggling) while `0.16.0` rejects it; the installed `uvicorn 0.15.0` does not cap `h11 < 0.16`, so a direct transitive pin is the least-invasive fix and avoids a `uvicorn` major bump. `data_transformation` is excluded (Azure Functions; no `uvicorn`/`h11`) | None material — a well-formed chunked control request returns 200 on both the vulnerable and patched parser, so legitimate traffic is unaffected |
| Reject blank/whitespace-only signing keys in `authentication_service`, `reporting_financials_service`, and `reporting_metrics_service` | Rely on the existing `min_length=32` guard alone | A 32-character all-whitespace key passes a length check but carries no entropy and is trivially predictable (CWE-798/CWE-259); a whitespace-rejecting guard fails closed and mirrors the required-and-validated secret pattern used by the other services | Deployments must supply a real, non-blank key (already implied by the min-length guard) |
| Restrict `JWT_ALGORITHM` to the HMAC allow-list `{HS256, HS384, HS512}` in `reporting_financials_service` | Leave `JWT_ALGORITHM` unvalidated | An unvalidated algorithm field permits `none` or an asymmetric-confusion value (CWE-347); an allow-list validator fails closed on `none`/unknown values while preserving the default `HS256` | None material — the default and all supported HMAC variants remain accepted |
| Require `API_KEY` from the environment and reject the shipped `<your_api_key_here>` placeholder (and blank/whitespace) in `reporting_financials_service` | Remove only the insecure default | `.env.sample` ships the placeholder, so removing the default alone still lets the placeholder resolve at runtime (CWE-798); a validator that rejects blank and the exact placeholder fails closed | Deployments must supply a real `API_KEY` value |
| Make no code change for CFG-08 (gateway CORS startup) | Alter the gateway CORS environment handling to resolve a reported startup conflict | The reported conflict is not reproducible: the gateway boots and `/health` returns 200 with only the documented comma-format `CORS_ALLOW_ORIGINS`, the auth cross-import reads the same variable, and the observed "Error importing authentication routers" is a pre-existing non-fatal `print` unrelated to CORS (AAP §0.5.3) | None — no behavioral change was required |
| Defer pre-framework-rejection security logging (OBS-01) | Restructure the OAuth2 dependency to log FastAPI's automatic 401 for a missing/malformed `Authorization` header before framework rejection | All three AAP §0.5.2 security events (authentication-failure, token-validation-failure, CORS-rejection) are already emitted on both public services; capturing the pre-rejection 401 requires an OAuth2 flow restructure with behavioral/regression risk beyond the security-fix scope (AAP §0.7.4/§0.8.2) | The framework's automatic 401 path remains unlogged pending the noted follow-up |
| Convert the financials real-app CORS test from a non-strict `xfail` to a real mutation-killing assertion | Keep the `xfail` guard | The import defect the `xfail` guarded is resolved (`main.create_app` imports cleanly), so the marker produced a silent XPASS; removing it and asserting the wildcard-with-credentials invariant makes the test fail if the CWE-942 mutation is reintroduced | None — verified to pass against the real factory and fail under the wildcard mutation |
| Correct the pipeline comment that mis-stated the function-app deploy runtime as `PYTHON\|3.9` | Leave the comment unchanged | `infrastructure/terraform/main.tf` sets the function-app runtime to `PYTHON\|3.11`, which satisfies the `>= 3.10` requirement of the patched `requests`/`urllib3` pins; the comment now states the accurate value and drops the moot alignment follow-up | None — comment-only change |
| Keep the minimal, factual CVE/CWE/advisory code annotations and decline wholesale removal; this log remains the single source of truth for decision rationale | Strip all in-code security annotations to force rationale exclusively into this log | AAP §0.9.3 explicitly permits code comments that name the control and its CVE/CWE identifier; the ~49 annotations are factual and point to this log for rationale rather than duplicating it, and removing them across ~15 files would be a broad, non-minimal change that worsens the over-scope finding | Readers must consult this log for full rationale; code carries only factual identifiers |
| Extract the `api_gateway` `/protected` bearer token via a single `OAuth2PasswordBearer` header dependency in the deployed `main.py get_current_user` (commit 655a630) | Keep the prior `Depends(validate_token)` that bound the raw token as a query parameter and then validated it twice | CWE-598: binding the token as a query parameter exposes it in URLs, server access logs, and browser history; a single header-based OAuth2 dependency mirrors the `authentication_service` pattern, decodes exactly once, and lets `/protected` return 200 for a valid bearer. The change is confined to the deployed `main.py` factory used by the module-level `app = create_app()` | The equivalent double-validate / query-parameter pattern still exists in the NON-DEPLOYED alternate factory `app/__init__.py` (F-APPVAR-1; not the ASGI entrypoint), so unifying it and adding full `Authorization` header-shape validation is the architectural authentication rework the AAP defers (§0.8) |
| Create `reporting_metrics_service/app/database.py` (SQLAlchemy engine, session factory, request-scoped session dependency) and `app/schemas.py` (dedicated Pydantic response models) (commit 655a630) | Leave the service returning ORM models directly with no session dependency (its state at the committed baseline) | The reporting-metrics service — one of the two in-scope container-hardened services — could not import and start cleanly and returned ORM models directly; adding a request-scoped session dependency and dedicated response schemas is the least-invasive way to make the in-scope hardened service actually runnable and its security controls verifiable at runtime | The two new modules are small and self-contained and do not alter any security control; broader data-layer refactoring remains out of scope (§0.8) |
| Add a finite `timeout=30` to the `data_transformation` outbound FX-rate `requests.get` call in `main.py` (commit 655a630) | Leave the outbound request without a timeout | CWE-400: an outbound HTTP call with no timeout can block indefinitely on a slow or unresponsive upstream and hang the function invocation; a finite timeout fails fast and bounds the call while the patched `requests` pin addresses the dependency-layer advisories separately | A legitimately slow upstream (over 30 seconds) now raises a timeout error instead of hanging — the intended, safer behavior |
